# MetricGuard working instructions

Read [docs/project-graph.md](docs/project-graph.md) first for a small map of the product, code, and source documents. The entire planning pack describes **one v1**: M0–M5 are milestones and MG01–MG26 are work items. Use [docs/v1-release-evidence.md](docs/v1-release-evidence.md) for v1 status and [docs/v2-release-evidence.md](docs/v2-release-evidence.md) for the later locally implemented v2; its two-real-case pilot gate is still open. Consult a planning chapter only when the task needs its detailed contract.

The generated code graph is [graphify-out/graph.json](graphify-out/graph.json). Before broad code browsing, ask a focused question with `graphify query "<question>" --budget 800`, or use `graphify explain "<symbol or file>"` / `graphify path "<A>" "<B>"`. Then inspect the returned source files and tests. The graph is navigation evidence, not a substitute for current source or tests. [graphify-out/GRAPH_TREE.html](graphify-out/GRAPH_TREE.html) is a browsable view. If Graphify is unavailable, follow the project map and use `rg`.

**Graphify performance policy (2026-10-04):** Refresh the graph manually after a batch of changes, only when the user requests the refresh. Do not run Graphify after every edit, on save, on workspace open, or as a background watcher. Honor the root `.graphifyignore`; retain `graphify-out/cache/` so refreshes can reuse cached extraction. For an authorized refresh, set `$env:GRAPHIFY_MAX_WORKERS = '1'` and run `graphify update . --no-cluster` from the repository root; keep the resulting `graphify-out/graph.json` and `graphify-out/manifest.json` with the change. Do not run multiple refreshes concurrently. The installed update command has no supported indexing-depth or `--no-viz` flag; `--no-cluster` skips clustering and HTML rendering. Regenerate `GRAPH_TREE.html` only on a separate explicit request, not as part of routine refreshes. Until a manual refresh, treat the generated graph/tree as potentially stale and confirm navigation against current source. If a change alters a component boundary, data flow, or the state of a v1 or v2 requirement, also update `docs/project-graph.md` and the relevant release-evidence file. Do not run `extract`, `cluster-only`, or `label` as part of routine refreshes.

Verify behavior with the relevant tests before reporting completion. Full local checks are `.venv\Scripts\python -m pytest -q --basetemp .test-tmp/full`, `npm run build --prefix apps/web`, and `docker compose -f infra/compose.yaml config --quiet`. When Docker is available, run `.venv\Scripts\python -m scripts.verify_live_runner --output data/evaluation/live_runner_report.json` and distinguish its covered paths from untested live failure modes.
